# Theme Switcher

Replace hue-named colors with role-named tokens, generate their ramps in OKLCH, and make
the whole app repaint from a set of CSS custom properties on `:root` — no rebuild, no class
swap.

Second of three specs. Requires **`tailwind-4`** (every theme token must already be a real
custom property). Followed by **`display-configurator`**, which adds user-facing pickers on
top of the mechanism built here.

## The problem with the current palette

`ocean` tells you a color is blue. It does not tell you where it may be used. When a theme
flips, `bg-ocean-600` becomes a lie — `bg-primary-600` does not.

Worse, brand vocabulary (`primary`/`secondary`/`accent`) has no concept of what a color is
painted *on*. It cannot express "pale grey text on dark grey" as a guaranteed relationship,
which is exactly what a readable dark theme is.

## Core rule: tokens come in pairs

Every background token has a matching foreground token. They are chosen together, never
independently. This is what makes a theme safe to hand to a user in spec 3 — an unreadable
combination becomes unrepresentable, because nobody ever picks a text color against an
unknown background.

## Token vocabulary

**Surfaces** — by elevation, not by color:

| Token | Use |
|---|---|
| `surface` | page background |
| `surface-raised` | cards, dropdowns, nav bar |
| `surface-sunken` | table stripes, wells, code blocks |
| `surface-overlay` | modals, popovers |

**Content** — by emphasis; each must be legible on any surface above:

| Token | Use | Today |
|---|---|---|
| `content` | body text | `navy-900` (26 uses) |
| `content-muted` | labels, metadata, inactive tabs | `gray-500`/`gray-700` |
| `content-subtle` | placeholders, disabled | `gray-400` |

**Lines:**

* `border` — default hairline
* `border-strong` — inputs, table dividers
* `focus` — **its own token, not an alias of `primary`.** 71 `focus:ring-ocean-500` plus 36
  `focus:border-ocean-500` usages today; it has its own contrast rules and a theme may well
  want to move it independently.

**Interactive** — each with its content pair:

* `primary` / `primary-content`, plus `primary-hover`, `primary-active`
* `accent` / `accent-content` — the active-navigation indicator (`flame`'s old job, wearing
  `fuchsia` as a placeholder after spec 1)
* `highlight` / `highlight-content` — search-result and table-row highlights (`sun-200`,
  `sun-400`)

**Status** — same pairing, plus a tinted background:

* `danger` / `danger-content` / `danger-surface`
* likewise `warning`, `success`, `info`

~24 tokens. More than four; far fewer than five ramps × eleven shades.

## Ramps in OKLCH

A ramp is lightness stepping at fixed chroma and hue: `oklch(L C H)`. Because `L` is
perceptually uniform, steps are visually even across every hue and contrast becomes
predictable — neither is true of the hand-eyeballed sRGB ramps in
`tailwind.config.js` today (generated by an earlier session from the coolors palette
`8ecae6-219ebc-023047-ffb703-fb8500`, which is why 9 of 11 shades per ramp are unused and
`flame-500` sits at 2.48:1 on white).

Generation lives in a `ThemeRamp` support class (`app/Support`, following `PlotlineColors`)
— anchor color in, eleven shades out. Testable, and the same code spec 3 calls from the
picker.

> [!WARNING]
> Contrast needs a **ceiling, not just a floor**. Pure white on pure black is 21:1 and is
> *worse* for astigmatism — halation makes light text bloom into the background, and the
> sharper the contrast the more it smears. Target ~7–12:1 for body text; reject below 4.5:1
> and warn above ~15:1.

> [!NOTE]
> Clamp chroma on accents in dark themes (~0.12 in OKLCH). Saturated colors at high
> lightness are what make a dark theme painful to look at. Trivial to enforce in the ramp
> generator, impossible to express in hex.

Contrast rules differ per token type: 4.5:1 for anything with a `-content` pair, 3:1
(non-text UI) for `accent`, `border`, `focus`.

## Runtime mechanism

* `@theme` defines the role tokens and emits them as custom properties on `:root`.
* A generated `<style>` block in the layout head, **after** the Vite stylesheet, overrides
  those properties for the active theme. ~1KB — no extra request, no FOUC.
* Cache the rendered block; bust on theme change. Do not recompute ramps per request.

Opacity modifiers need no special handling: v4 compiles `bg-primary-500/50` to
`color-mix(in oklab, var(--color-primary-500) 50%, transparent)`, so a variable holds a
plain hex or `oklch()` value. The v3 `rgb(var(--x) / <alpha-value>)` channel-triplet
workaround is not needed and must not be reintroduced.

> [!WARNING]
> `@theme inline` bakes values into utility rules instead of referencing the custom
> properties, silently breaking every runtime override. Always plain `@theme`.

## Presets

Ship 3–4, seeded as rows. Most users never open a picker, and a preset built for eye strain
is worth more to the people who need it than the picker in spec 3.

* **Daylight** — the current look, ported
* **Dusk** — dim, moderate contrast
* **Low-glare dark** — dark grey surfaces, pale grey content, chroma-clamped accents.
  Deliberately *not* black-on-white inverted.

**The dark preset is not optional decoration — it is how the vocabulary gets validated.**
`surface` and `surface-raised` collapsing into one value, or a missing `content-muted`, only
becomes visible when a second theme exists. Build it alongside the rename, not after.

## Migration

286 usages across Blade and JS: `ocean` 205, `navy` 40, `aqua` 29, `flame` 7, `sun` 2.

Each has to be re-read as a question — *is this `primary`, or is it just blue?* Notably,
`ocean` is two roles wearing one name: ~115 of its uses are `focus:ring`/`focus:border` and
belong to `focus`, not `primary`.

Keep the old ramps as the Daylight preset's *values* during migration, so the default theme
stays pixel-stable while names change underneath.

## Out of scope

* Pickers, per-user custom themes, fonts, sizing — spec 3.
* The v4 port itself — spec 1.

## Open questions

* **Per-user or global?** Per-user is the obvious answer — but the login and registration
  pages have no user. Cookie, or a fixed default for guest layouts? (Note `CrawlerSetting`
  is the precedent for a global singleton, and is explicitly *not* the model here.)
* **Does `dark:` survive?** Either dark mode is a variant or it is just another theme.
  Having both is how theme systems rot. Pick one.
* Does `prefers-color-scheme` select a default preset for logged-out visitors?
* Storage shape — anticipating spec 3, a `themes` table with a `tokens` JSON column and an
  `is_preset` flag rather than 24 columns, so the token list can grow without a migration
  each time. It will grow.

## Done when

* No hue-named color remains in Blade, JS, or `app.css`.
* Ramps generated by `ThemeRamp`, unit-tested, with contrast assertions per token type.
* Three presets selectable; switching repaints without a rebuild or a page rebuild artifact.
* Every page walked in a browser under **each** preset.
* `documentation/architecture.md` gains a *Theming* section; deep dive in
  `documentation/theming.md`.
