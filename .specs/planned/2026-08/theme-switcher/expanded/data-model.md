# Theme Switcher — data model

## The storage decision

**Exactly one value in this feature varies at runtime: which preset is active.** A preset's
tokens, its name, its contrast ceiling and its chroma clamp are all authored by hand and
change only when someone edits a file. So presets live in `config/themes.php`, and the
database holds one string.

The rejected shape was a `themes` table whose rows were "the runtime copy" of config. It buys
a foreign key and costs a seeder, `updateOrCreate` drift between config and rows, a lazy
fallback for un-seeded installs, a key-validation `saving` hook, a `deleting` guard for
presets, and a cache key derived from `updated_at` — all to store values nothing queries.
Same reasoning that keeps the contrast ceiling out of a column, one level up.

`display-configurator` (spec 3) introduces a `themes` table when a row genuinely varies per
user. That is the point at which it earns its schema, and it is one migration in a pre-V1 app
whose recorded convention is that destructive migrations are fine while the only data is the
Melusine seed.

## `users.theme_slug` — the only schema change

**Resolved in the grill: per-user, no settings table at all.** There are no guests past the
login page except `/shared/scenes/{token}`, so every themed view has a known user.

| Column | Type | Notes |
|---|---|---|
| `theme_slug` | string, **nullable**, no default | `null` = follow `config('themes.default')`. Validated against `array_keys(config('themes.presets'))` — never a free string. |

Nullable rather than copying the default in at registration, so changing the default still
reaches every user who never picked.

Resolution, in `<x-theme-style />`:

```php
auth()->user()?->theme_slug ?? config('themes.default')
```

Unauthenticated surfaces — the share page, login, `/` — therefore get the config default. A
stranger holding a share link sees the neutral look, not the author's accessibility theme.

- A stored slug that no longer names a preset falls back to the default and logs. A config edit
  must not white-screen every page.
- No singleton: the site default is one line of config, and this is self-hosted, so changing it
  is a file edit. Spec 3 adds the `themes` table when a row genuinely varies per user.

## `config/themes.php`

Source of truth for what a preset *is*.

```php
'default' => 'daylight',
'contrast' => ['floor_text' => 4.5, 'floor_non_text' => 3.0, 'default_ceiling' => 15.0],
'presets' => [
    'daylight'       => ['name' => 'Daylight',        'tokens' => [/* literal current values */]],
    'dusk'           => ['name' => 'Dusk',            'tokens' => [...], 'contrast_ceiling' => 12.0],
    'low-glare-dark' => ['name' => 'Low-glare dark',  'tokens' => [...], 'contrast_ceiling' => 10.0],
],
```

Every preset stores **final token values**, not anchors. Dusk and Low-glare dark's values are
generated by `php artisan theme:ramp` and pasted in (see `architecture.md`); the anchors and
chroma clamp that produced them belong in a comment above the block, not in a runtime array
that nothing reads.

### Contrast thresholds

- Floors (4.5 text / 3.0 non-text) are WCAG minimums, global, and **reject**.
- The ceiling is declared per preset, defaults to `config('themes.contrast.default_ceiling')`,
  and **warns** — halation is one reason to cap contrast, not the only reason to hold an
  opinion about the top of the band, and different conditions pull in opposite directions. A
  preset for low vision may want a higher ceiling than one for astigmatism; a hard-coded 15.0
  would make them the same theme in different hues.
- `ColorContrast::verdict()` takes the ceiling as an argument, so no constant creeps back in.

### `App\Support\ThemePreset` — value object

`readonly` — `slug`, `name`, `tokens`, `contrastCeiling`. Statics `fromSlug(string): self` and
`all(): array<string, self>`, both reading config. This is what `ThemeStyleBlock` and the
Appearance form consume, so neither of them handles a raw config array (CLAUDE.md: value
objects over magic arrays). One class, not a package.

## Reference data — `app/Support/ThemeTokens.php`

The canonical token list, following `PlotlineColors`. One place, so adding a token is a
one-line change plus a value in each preset.

```php
public const ALL = ['surface', 'surface-raised', 'surface-sunken', 'surface-overlay',
    'content', 'content-muted', 'content-subtle', 'border', 'border-strong', 'focus',
    'primary', 'primary-content', 'primary-hover', 'primary-active', 'link', 'link-hover',
    'accent', 'accent-content', 'accent-surface', 'neutral', 'neutral-content',
    'highlight', 'highlight-content', 'table-header', 'table-header-content',
    'nav', 'nav-content', 'nav-content-muted', 'nav-raised', /* status ×4 ×3 */ ];

/** Background => foreground, for the contrast matrix. */
public const PAIRS = ['surface' => 'content', 'primary' => 'primary-content', /* … */];

/** Tokens judged as non-text UI (3:1) rather than text (4.5:1). */
public const NON_TEXT = ['accent', 'border', 'border-strong', 'focus'];
```

Three flat lists read better than one nested array of metadata, and this is the file a junior
opens first.

Additions to `spec.md`'s table, all three forced by the code (rationale in `open-questions.md`):

- `nav` / `nav-content` / `nav-content-muted` / `nav-raised` — the nav bar is a dark band above
  a light page (`bg-navy-950` + `bg-ocean-900` + `text-aqua-100` over `bg-gray-100`), not an
  elevated surface (Q3).
- `link` / `link-hover` — 49 usages of `text-ocean-600` / `hover:text-ocean-800`, distinct from
  `primary`, which is `bg-navy-900` (Q4).
- `table-header` — `bg-sun-400` is `x-table`'s `<thead>` band on every table in the app, not a
  row highlight (Q9).
- `accent-surface` / `neutral` — `x-badge`'s `indigo` and `gray` variants become roles (Q10).
  `accent-surface` is also where `app.css`'s `purple` callout lands, since it has no status
  equivalent.

Roughly 32 tokens. Still far short of 5 ramps × 11 shades.

> [!IMPORTANT]
> **The eleven-shade ramps stop being public vocabulary.** Ramps are an *authoring* tool — a
> preset stores flat, final values, and Blade only ever names roles. There is no
> `bg-primary-600` after this spec; there is `bg-primary` and `bg-primary-hover`. This is the
> biggest readability win here and the thing most likely to be undone by habit during the sweep.

## Daylight is literal, the other two are generated

Daylight's tokens are the **current hex values**, copied across. That is what keeps the default
theme pixel-stable while names change underneath, and what makes the computed-style diff a
meaningful gate. Only Dusk and Low-glare dark are ramp output.

Regularizing Daylight onto even OKLCH ramps is deliberate follow-up work with its own browser
pass — not part of this sweep. Record it in `standing-issues.md` when shipping.

## Migration impact

One `add_theme_slug_to_users_table` migration adding a nullable string. Nothing backfills, no
new table, no seeder. A fresh install paints correctly with no rows touched at all, because
`null` resolves to the config default.
